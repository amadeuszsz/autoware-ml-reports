Driving-Aware Perception Metrics

Our mAP and mIoU improve week by week — yet a higher score does not mean the car drives more safely. This plan adds a metric set that weights every error by where it happens, when it could matter, and which box properties planning actually consumes.

Section 1

Why our metrics must change

Three real failure patterns from our fleet show the problem. Each pair has the same effect on mAP — and a completely different effect on driving.

False positives behind a fence

Dozens of false positives on parked vehicles behind a fence, outside any drivable area.

Driving impact: negligible — planning never interacts with them.

Metric impact today: large mAP penalty.

One miss in a crowd

A few pedestrian false negatives inside a dense crowd, versus completely missing a single pedestrian directly ahead of ego.

Driving impact: the single miss ahead is critical.

Metric impact today: both look identical.

Phantom on the median

A rare false positive of a pedestrian on the median strip — directly beside ego's lane.

Driving impact: emergency braking on an open road.

Metric impact today: statistically invisible.

The fix is not one new number. It is weighting and slicing errors along three axes:

WHEREIs the object on or near a drivable surface? On ego's path? (lanelet map, ego corridor)
WHENHow soon could ego and the object physically collide? (time-to-collision)
WHATAre the box properties planning consumes correct — yaw, corners, nearest surface, velocity — and stable over time?

What we measure today

APE autoware_perception_evaluation (product runtime)

  • Detection: mAP + mAPH with four matching modes — center distance, BEV IoU, 3D IoU, plane (nearest-surface) distance.
  • Tracking: CLEAR metrics — MOTA, MOTP, ID switches.
  • 2D: detection / tracking mAP, classification accuracy.
  • Sensing: point-cloud presence checks in detection / non-detection areas.
  • Prediction metrics: still WIP.
  • Segmentation (2D or 3D): none — see Section 9.

What neither repo has today:

no map / location awareness no time-to-collision weighting only mean errors — no max / percentile tails no temporal stability at detection level no boundary quality for segmentation no segmentation support in the runtime evaluator

The plan at a glance

Fifteen metrics across six families, each reported along three axes — distance-range bins, lanelet region variants (whole-scene · road · walkway — the region filter in Section 5), and the class taxonomy (per trained class vs behaviour groups — Section 6). Each links to its detail page in Section 7.

Region variants — the second evaluation axis. Lanelet masking is not a single metric; it is an axis applied to every metric here, det3d and seg3d alike, exactly as the distance-range bins are. Each metric is reported in four region slices: whole-scene (no map), road — everywhere the car drives: road, road_shoulder and crosswalk lanelets plus drivable-area polygons — walkway (pedestrian walkway lanelets), and both (their union). Section 4

One metric core, pluggable inputs

Both collision-risk metrics (the critical FP / FN curves and the collision-risk-weighted mAP) answer the same question — “how soon could this object and ego collide?” — with one shared computation: propagate ego and the object forward as reachable sets and take the first time they overlap. There is a single model — no fidelity levels. What is pluggable is only the input source behind one interface: offline eval-output here, live ROS messages in perception_evaluation.

A perception metric must not depend on how anyone drove. The recorded ego path and the observed motion of other agents each already encode a driving decision — the safety driver braking for the pedestrian our model missed, or a car that merely happened to be stopped. Score against them and planning leaks into a perception number: the model is rewarded for a hazard someone else avoided. Miss a pedestrian, the safety driver brakes, the recorded path swerves clear, TTC looks large; yet had the model driven it would not have braked and TTC would be near zero.

So no future is ever the recorded path or an observed velocity. Instead every agent — and ego — is propagated at the maximum speed the map allows over the surface its class may travel, and TTC is the first time the two reachable sets meet. Fully planner-independent, and deterministic from the map alone.

The reachability model

Ego and every dynamic agent expand into a reachable set that grows with the look-ahead time; a static object stays put. The set shape is per class:

ClassReachable setMax speed
car · truck · bus · train · motorcycle (and ego) the worst-case “hat” — everything reachable at max speed under the tightest feasible turn (bounded curvature), clipped to the drivable laneletslanelet speed limit
pedestrian · animal · bicycle an isotropic disc — free to move in any direction, over any surface a per-class “reasonable run” cap
barrier · traffic_cone · debris · bicycle_rack · vehicle_extension stationary — the object footprint; only ego approaches it0

TTC = the earliest look-ahead time at which ego's reachable set and the object's set overlap (stepped at dt), else ∞ within the horizon T. The horizon is grounded in stopping physics — reaction + braking from the lane speed limit (Section 13).

Cross-repo consistency — with realistic expectations. There is no shared metric library: autoware-ml and perception_evaluation implement the metrics independently, each from the versioned spec (Section 11). Agreement is enforced by cross-repo parity tests — on identical inputs the two implementations must produce the same numbers — not by sharing code. End-to-end replay is a different matter — it runs through ROS, where message timing, queue drops and callback ordering vary between runs. Full-pipeline numbers are therefore validated against tolerance bands (|Δ| ≤ ε per metric, ε spec-versioned), not bitwise equality. Drift beyond ε still means a bug.
Section 5

Evaluation filters

A filter is an optional, per-metric selector that decides which ground truth, predictions or points a metric sees before it runs. It is not a metric — it is an axis: the same metric under a different filter is a different reported slice, not a new number to invent. Three axes slice every metric in the catalog, and any of them can be combined:

  • the lanelet region filter (road / walkway);
  • the ego corridor filter (objects and points in the ego's forward path);
  • the built-in distance-range bins (near / mid / far rings around the ego).

The region and corridor filters are pluggable MetricFilters (more can be added without touching any metric); the distance-range bins are the suite's built-in radial windowing. Every metric carries an optional filter (default None = whole-scene) and is always also emitted per range.

Both map-backed filters need a scene's lanelet2_map.osm. A scene that ships no map is excluded from the filtered slices (an explicit availability check, not a swallowed error — a map that should parse but is corrupt still fails loud) while its objects and points still count in the whole-scene metrics. Each filter logs how many frames it ran on (covered / seen) so a slice computed over fewer scenes than the whole-scene metrics is visible, never silent — the class distribution of a filtered slice can differ from whole-scene when map coverage is partial.

The region filter

RegionFilter keeps only the elements inside a chosen set of lanelet2 regions, so any metric can be reported on the road or on the walkway — detection and segmentation alike. Because a crosswalk is where the car drives, it belongs to the road region; the pedestrian-only walkway is its own, lower-priority region. An optional margin (meters) adjusts the region border; a boolean expand picks the direction — false (the default) cuts inward, true grows outward. The default cut trims the strip along the outer border of the mapped surface (second figure below): border points are naturally noisy — high entropy, frequent misclassification — and would otherwise dominate a region's error metrics.

Regions & the math

A RegionFilter takes a list of literal lanelet2 tokens; the map provider unions every lanelet (by subtype) and area (by type) whose tag is in the list into that region's polygon. The presets:

road = [road, road_shoulder, crosswalk] (+ drivable_area / intersection_area / crosswalk_polygon)
walkway = [walkway]

A detection box belongs to a region when any part of its footprint overlaps it (so an object overhanging from an off-region center still counts); a segmentation point by point-in-polygon:

keep(box, M) = footprint(box) ∩ M ≠ ∅   (any overlap)
cut inward (expand: false):   keep(point, M) = point ∈ M  ∧  point ∈ (U ⊖ margin)
grow outward (expand: true):   keep(point, M) = point ∈ M  ∨  point ∈ ((M ⊕ margin) ∖ U)

margin (default 0.0) is a distance in meters; expand picks the direction and defaults to false — cut inward. The cut removes points near the outer border of the whole mapped surface U — the union of all regions — eroded inward by the margin (e.g. 0.2 m). Border points are naturally noisy (high entropy, frequent misclassification) and would otherwise dominate a region's error metrics. Crucially, the erosion is applied to the full union, never per region: an internal border between adjacent regions (road ↔ walkway) is interior to U and stays intact, so no dead gap appears between them — a point near that shared border keeps counting for its region. With expand: true the selected region instead grows outward by the margin, claiming only off-map points near it — never points inside another mapped region, so adjacent regions still do not overlap.

Every metric — det3d and seg3d, all families — is then computed on each region's kept set, exactly as it is per range bin. Whole-scene and every region slice are always published together (see Section 11).

Declaring a filter in config

Filters are optional and hydra-instantiated — list a metric once per region you want; each filter type carries its own kwargs. filter: None (the default) is the unchanged whole-scene metric.

- {_target_: …tp_errors.TpErrors, stages: [test]}  # whole-scene
- {_target_: …tp_errors.TpErrors, stages: [test],
   filter: {_target_: …metrics.filters.RegionFilter, region: [road, road_shoulder, crosswalk]}}
- {_target_: …tp_errors.TpErrors, stages: [test],
   filter: {_target_: …metrics.filters.RegionFilter, region: [walkway]}}

The suite groups components by filter, builds one filtered sub-state per (range, filter) so the shared match curves are reused, and prefixes each filtered metric's keys with the filter name (road/mATE_…). Two metrics that differ only by filter therefore never collide.

Implementation notes
  • Map data is already in the dataset: gen2 scenes ship map/lanelet2_map.osm with local_x/local_y node tags — already in the map frame that ego poses use, no geodetic projection needed.
  • Preprocess once per scene: OSM → per-region polygons (shapely) unioning lanelet relations (left+right bounds) and area/polygon ways → cached .npz/GeoPackage, exposed as a T4Devkit accessor.
  • Boxes/points are in base_link → transform to the map frame with the stored ego pose; RegionFilter.required_eval_keys = (ego2global, scene_token), folded into the suite's fail-loud check.
  • Implemented once as a shared filter axis (both suites), so a new metric inherits the road / walkway slices for free — never re-implemented per metric.
  • Availability: older DBs (db_j6_v3, db_j6_v5, db_largebus_v1, …) have no map/ directory. A region filter is declared per-dataset and fails loud where the map is absent — never silently collapsing to whole-scene.
  • Caveat from real maps: walkway is sparse (≈1 lanelet/scene); most pedestrian space is crosswalk, which sits in the road region — so the standalone walkway slice is often near-empty by design.

The corridor filter

A second filter type on the same axis: CorridorFilter keeps only the elements in the ego's reachable path — the curvature-bounded region reachable within the horizon at the max map-legal speed, clipped to the road lanelets, so the corridor follows the road through bends instead of shooting straight off it into off-road objects. It is the ego reachable region of the one collision model (curvature-bounded, clipped to the road), planner-independent — not the path the vehicle happened to drive (Section 4): the driver already steered around the hazard the model missed. This is the "in ego's path" slice, and like the region filter it composes with any metric, det3d and seg3d alike: yaw error for in-path objects, mAP in the corridor, segmentation IoU / error clusters / uncertainty on the road ahead. It is the filter form of the same corridor the critical FP / FN curves use; where those are a dedicated curve, the corridor filter lets every other metric be reported in-path too.

The math & config

Corridor C = the ego reachable region of the one collision model (Section 4): the curvature-bounded set reachable within the horizon T at the max map-legal speed, clipped to the road lanelets. An element is kept when it lies in C — equivalently, when its reachability TTC ≤ T:

keep(e) = TTC(e) ≤ T   (e in ego's reachable region on the road)
filter: {_target_: …metrics.filters.CorridorFilter, map_provider: …, region: [road, road_shoulder, crosswalk], horizon_s: 4.0}

It needs the current ego pose (ego2global) and the scene's lanelet map. No recorded future and no observed agent velocity enter — the region is the worst-case reachable set on the road.

The range filter (distance bins)

Every metric is also reported per distance ring around the ego, because a model that wins overall can still regress far away where points are sparse. This is not a pluggable MetricFilter but the suite's built-in radial windowing: a metric is computed once whole-area and once per MetricRange, its key suffixed with the band. The bands used here are 0–50 m, 50–90 m, 90–121 m, and the full 0–121 m. Distance is the horizontal (BEV) range from the ego, so it composes with the region and corridor filters: e.g. "road, 50–90 m" is one slice.

ranges: [{name: 0-50m, 0.0, 50.0}, {name: 50-90m, 50.0, 90.0}, {name: 90-121m, 90.0, 121.0}, {name: 0-121m, 0.0, 121.0}]
Section 6

Classes and taxonomy

Detection and segmentation are trained and scored over fixed class sets, mapped from the raw T4 annotation names at data-load time by an explicit name_mapping (raw → final class; a category left unmapped or set to null is ignored, so a dataset's extra categories never break loading). Every per-class metric in the catalog is reported over these classes and, in parallel, over the behaviour taxonomy that folds them into driving-equivalent groups.

det3d — 13 classes

car · truck · bus · train · motorcycle · bicycle · pedestrian · animal · barrier · traffic_cone · debris · bicycle_rack · vehicle_extension.

Representative folds at load: emergency / forklift / kart / police / ambulance → car; construction / tractor / fire-truck → truck; pushable_pullable → debris; open-door / protruding object → vehicle_extension; the pedestrian sub-types → pedestrian. trailer is geometrically merged into its towing truck. Boxes are filtered by point count and per-class eval range before scoring.

seg3d — 20 classes

the 13 detection classes, plus drivable_flat · non_drivable_flat · vegetation · building · vertical_thin · static_clutter · noise.

Surface / structure folds: drivable-surface / drainage → drivable_flat; sidewalk / curbs / other-flat → non_drivable_flat; poles / lights / signs / bollards / flags → vertical_thin; manmade → building; solid- / other-stuff → static_clutter; noise / ghost-point → noise. background, ego_vehicle, out_of_sync and unpainted map to the ignore index and are excluded everywhere.

The behaviour taxonomy

Not every misclassification changes how the vehicle drives. A bus predicted as a truck is still a large vehicle to yield to; a stroller predicted as a pedestrian is still a vulnerable road user. So every metric is reported over two class taxonomies, and the taxonomy is a report axis exactly like the region, corridor and distance axes above:

  • Per class — every trained class scored on its own; a car read as a truck is a false positive for one and a false negative for the other. The strict view the model is optimised against.
  • Behaviour groups — classes whose confusion does not change the driving decision are folded into one group, so intra-group confusion becomes a true positive. It isolates "did the model see the kind of thing that matters" from "did it name it exactly".

A single class_groups key declares the taxonomy — a full partition of the trained classes, each group named with a grouped_ prefix (even singletons such as grouped_debris, so a group name is always unambiguous):

class_groups:  # seg3d
  grouped_vehicle: [car, truck, bus, train, vehicle_extension]
  grouped_structure: [building, vertical_thin, bicycle_rack]
  grouped_flat: [drivable_flat, non_drivable_flat]
  • Always a replace, never additive. When a suite is built with class_groups, labels are relabeled to their group and scores are marginalized (summed over members) before the metric runs, so the group takes the members' place everywhere — per-class rows and aggregates (mIoU, accuracy, mAP) alike.
  • The suite runs twice, not the metric. Each suite is instantiated once per-class and once grouped (a distinct _grouped logging prefix), so the two taxonomies never collide in the key namespace. Duplicating the suite keeps each pass a straight, single-taxonomy computation.
  • Filters first, fold second. The ground-truth filters (point count, range) act on the trained classes; the fold happens afterwards, at metric time — so the two taxonomies count the same objects and points, only labelled at a different granularity.
  • Full partition, forward-compatible. The groups must cover every trained class (an unassigned class fails loud). A member that is not currently trained is simply skipped, so a group can name a class the model will only learn later without breaking the current run.

Metric catalog

One page per metric. The plain-language part is for everyone; expand “The math” and “Implementation notes” if you build it.

Corner displacement error (combined)

AMLAPEdet3d

Position, size and yaw errors interact — a box can have a perfect center and still put its corners in the wrong lane. Corner displacement folds all three into one number in meters, measured where planning collides with things: the box outline. It is the combined true-positive geometry metric — a 3° yaw error on a 20 m truck shifts a corner ~0.5 m, and that shows up here directly, no separate yaw statistic needed. Center-distance matching is also blind to footprint inflation — an oversized box scores the same as a tight one; corner distance penalizes it. The one thing it deliberately forgives is a 180° heading flip (the outline barely moves) — the heading-flip rate catches that separately.

The math

For a matched pair, take the four BEV corners of each box with the cyclic corner assignment that minimizes the sum of distances (so a 90°-symmetric parameterization is not unfairly punished):

CDE = (1/4) · Σi=1..4 ‖ c_pred,(i+k*) − c_gt,i ‖ ,   k* = argmink∈{0..3} Σ ‖·‖

Reported per class × range bin: mean / p95 / max. Corner-shift intuition for a length-L object under small yaw error δ (radians):

corner shift ≈ (L / 2) · δ   →   L = 20 m, δ = 3° : ≈ 0.52 m

Corner matching mode: additionally, AP can be computed with mean corner distance as the match cost instead of center distance (adopted from arXiv 2507.00190). Same thresholds {0.5, 1, 2, 4} m; a configuration flag, not a separate implementation.

Implementation notes
  • Corner math is shared with the signed nearest-surface error and the export-side box utilities — one geometry helper, used by all.
  • Matching-mode flag extends the existing center-distance matcher; both modes share the PR-curve machinery.
  • APE already supports pluggable matching modes — add corner distance as a fifth mode with identical spec.

Heading-flip rate

AMLAPEdet3d

A 180° heading flip leaves the box outline almost unchanged, so corner displacement forgives it — but it inverts the object's velocity direction and is a prime cause of tracking failures. This metric isolates exactly that: any true positive whose heading error passes a quarter turn counts as one flip — a uniform +1, however far past 90°, because a wrong-way heading is wrong-way regardless of degree.

The math

Over the true positives at the TP threshold, with the wrapped yaw error Δψ = |wrap(ψ_pred − ψ_gt)| ∈ [0, π]:

flip_rate = #(TP with Δψ > π/2) / #TP ,   each flip contributes a uniform +1

Reported per class × range bin as the flip rate and the raw flip count; the penalty is a step at 90°, so 91° and 179° weigh the same. π/2 is the spec-versioned threshold.

Implementation notes
  • Reads orientation_error from the shared match curve — no new matching, pairs with the corner displacement error.
  • Same yaw convention as APH, so the two heading signals stay consistent.

Signed nearest-surface error

AMLAPEdet3d

Stopping distance is computed against the nearest face of an object, not its center. The same 1 m center error is harmless if the box is too long at the back, and dangerous if the near face is placed 1 m too far away — ego brakes late. The sign of this error is the safety signal. The measure is radial — the distance from the ego origin to the nearest point of the box footprint — so it applies to objects in any direction (beside and behind, not only ahead); the figure shows an object in front for clarity.

The math
err_ns = d_pred − d_gt ,   d = distance from ego origin to the nearest point of the BEV box outline

Positive = predicted farther than reality → late braking (safety). Negative = predicted nearer → over-caution (usability). Reported per class × range bin as signed tails: p5 / p95 / max|·|, plus the mean.

Implementation notes
  • Reuses the corner-displacement geometry helper; nearest point on a rectangle is closed-form.
  • In APE, align the definition with the existing plane-distance matcher so numbers are mutually interpretable — one shared definition of “near face”.

Critical FP / FN curves (ego corridor)

AMLAPEdet3d

Two numbers we never average: false positives in ego's path cause phantom braking (usability); false negatives in ego's path mean driving toward something we can't see (safety). "Critical" is the one reachability model (Section 4): an object is critical when it can collide with ego within the horizon — its reachable-at-t set meets ego's at some t ≤ T, i.e. TTC ≤ T. That covers an object standing in the path, a crossing pedestrian and an oncoming vehicle, while a same-speed lead is excluded. Both are reported as curves over the confidence threshold — release engineering picks a threshold and needs to know if any threshold is acceptable on both axes at once.

Reported per class (and per behaviour group), because a missed pedestrian is not a missed cone — the counts are broken down so the safety-critical classes stand on their own. Matching is class-agnostic (nearest box within the threshold, any class), so an object detected as the wrong class still counts as detected — it does not become a critical FN. That mislabelling is captured by the confusion matrix, not here; this metric answers only "is there a box in the path at all".

The math

An object is critical when its reachability TTC to ego is within the horizon (Section 4): TTC(x) ≤ T, T = 4 s. For each confidence threshold τ:

critical(x) = TTC(x) ≤ T
FP_crit(τ) = #(unmatched predictions ≥ τ that are critical) / frame
FN_crit(τ) = #(unmatched GT that are critical) / frame

Published as two curves plus their values at the release operating point. Never combined into one score: one axis is usability (可用性), the other is safety (安全性).

Implementation notes
  • Shares the one reachability engine with the collision-risk-weighted mAP — the per-object TTC is computed once per frame and both read it.
  • In APE online mode ego's future comes from the planned trajectory instead of the reachable set; same code path via the ego-future provider (Section 4).
  • Reported per class; pedestrian FN-in-corridor is the headline safety number.

Collision-risk-weighted mAP

AMLAPEdet3d

The flagship metric: every object's contribution to precision and recall is weighted by how soon it could collide with ego, from the one reachability model (Section 4). An object that cannot be reached within the horizon weighs ≈ 0 — so a same-speed lead, or scenery off the road, no longer buys score, while an imminent, in-path object dominates it.

The math

TTC comes straight from the reachability model (Section 4): ego and the object are each propagated at their class's maximum map-legal speed — ego and wheeled agents as curvature-bounded fronts clipped to the drivable area, VRUs as isotropic discs, static objects as their footprint. TTC is the earliest time t at which the two reachable-at-t sets overlap, else ∞. Two steps: reject cheaply if the sets cannot meet within T, otherwise step t up and return the first overlap.

w(o) = e^(−λ · TTC(o)) ,   λ = 0.5,   T = 4 s   (spec-versioned)

Weighted PR: each TP/FN contributes the weight of its GT object; each FP the weight computed from its own predicted state (class, pose). Weighted precision/recall → weighted AP, per class, per range bin.

precision_w(τ) = Σ_TP w / (Σ_TP w + Σ_FP w) ,   recall_w(τ) = Σ_TP w / Σ_GT w

Dropped by design: the DTT (distance-to-trajectory) factor — superseded by range-binned reporting of the TTC-weighted score, which matches our existing range-bin machinery.

Implementation notes
  • Shares the one reachability engine with the critical FP / FN curves — the per-object TTC is computed once per frame (map frame, drivable polygon from the lanelet map) and both metrics read it.
  • FP weighting propagates the prediction's own state under the same rule — a phantom that could reach ego is weighted like a real object there, which is the point (phantom braking).
  • Ego and wheeled agents take the lanelet speed_limit at their position (from the map, km/h → m/s), falling back to a spec-versioned constant off-map; VRUs use a per-class run speed. The turn radius is friction-limited, R = v²/alat.
  • Always published alongside the unweighted mAP (Section 11). A weighted-only report is not valid.
  • Weight and TTC per object are exported into the eval-output artifacts so per-scene debugging can rank the costliest errors.
Implementation notes
  • The provider needs only the current state plus dynamic bounds — per-class maximum acceleration and speed cap, and the lane speed limit for ego; it does not depend on any observed velocity.
  • FP weighting propagates the prediction's own state under the same worst-case rule — a phantom that could reach ego's path is weighted like a real object there, which is exactly the point (phantom braking).
  • Always published alongside the unweighted mAP (Section 11). A weighted-only report is not a valid report.
  • Weight and TTC per object are exported into the eval-output artifacts so per-scene debugging can rank the costliest errors.
  • APE consumes the same shared metric core (parity rules in Section 4); online mode swaps only the ego-future provider.

Occlusion-aware recall split

AMLdet3d

A miss on an object with no LiDAR return is a physics problem; a miss on a visible object is a model problem. The same detection suite is run twice with different ground-truth point-count floors — the visible split keeps GT with ≥ 1 LiDAR point, the overall split keeps everything including fully occluded boxes — and the gap between their recalls isolates the occlusion effect from genuine detection failures.

Definition & implementation
  • Two extra suite instances (det3d_visible, det3d_overall) differing only in min_num_points (1 vs 0); each reports the standard AP family over its GT set.
  • The main suite's own floor (min_num_points: 2) stays the release number; the split is diagnostic context for its recall.
  • No extra matching cost beyond the two suites — they reuse the standard per-suite machinery.

Detection stability per instance

AMLAPEdet3d

A detector whose boxes jitter frame to frame poisons tracking even if every single frame looks fine in mAP. The dataset's GT instance tokens let us follow one physical object across frames without any tracker — and measure how consistently the detector sees it.

The math

Group matched TPs by GT instance_token. For each instance with consecutive matched frames, form the error series e_t (yaw error, size error, center error) and measure its frame-to-frame variation — GT motion cancels out because we differentiate the error, not the state:

jitter(x) = std_t( e_t − e_{t−1} ) ,   e_t = x_pred,t − x_gt,t   (yaw wrapped)

Plus the flip rate: fraction of consecutive frame pairs where the yaw error jumps across ±π/2 — the failure mode that actually breaks trackers. Aggregated per class × range bin.

Implementation notes
  • Requires per-sample instance tokens in the eval output — a small extension of the stored detection state.
  • Sequential accumulation must respect scene boundaries (scene token already propagated in the infos).
  • APE computes the same statistics on tracker output, which is the authoritative runtime version; the AML version is the early-warning signal during training.

Consecutive-miss streaks

AMLAPEdet3d

Missing an object once for a single frame is noise; missing the same object for two seconds straight is a blind spot. The spec sheet already tracks this at runtime — we compute the identical quantity offline from instance tokens, so it can gate training runs, not just releases.

The math
streak(instance) = longest run of frames where the GT is inside evaluation coverage but unmatched

Reported per class: max and p95 streak length (frames and seconds at the annotation frequency), and the rate of streaks ≥ k frames. Combined with the corridor filter: streaks inside the corridor are the critical subset.

Implementation notes
  • Same instance-token grouping as the per-instance stability metric; one accumulation pass serves both.
  • Coverage check (range cap, min points) must be applied per frame so a departing object does not fake a streak.

Error clusters (phantom obstacles)

AMLAPEseg3d

An error is simply a point whose prediction disagrees with the ground truth — no class partitioning. What makes an error dangerous is where it happens, and that comes from the region filter (Section 5), never from segmentation class sets: on the road slice these are the phantoms that brake the car and the mislabeled obstacles that hide it. Nearby error points merge into one cluster, and each cluster counts once regardless of size.

The math

Within the attached filter's region (whole-scene when unfiltered), per range bin:

error rate = #(points with pred ≠ GT) / #(valid points)

Cluster level: connected components of error points (radius ε, spec-versioned). Each cluster counts as one phantom regardless of size — a lone stray point and a ten-point blob both cause a single emergency stop, so they carry the same penalty (default minimum cluster size = 1; nearby points merge into one phantom). Reported as counts and counts per frame.

Implementation notes
  • Clustering runs on error points only (a tiny subset), so cost is negligible; same voxel-hash neighborhood code as the neighbourhood-tolerant error rate.
  • Per-class breakdown by the points' ground-truth class — consistent with every other per-class point metric (what the misclassified thing really was).

Small-object partial-detection score

AMLAPEdiagnosticseg3d

For a pedestrian or a traffic cone, classifying even a handful of points correctly is far better than classifying none — downstream logic can still react. mIoU cannot see this: it averages over points and is dominated by large classes. This metric asks, per small object: did we see it at all? The first correct point earns roughly half the credit — existence — and further points saturate toward one.

The math

For each GT box of a small-object class, count its interior LiDAR points n and those with the correct predicted class k. The credit uses a normalized saturating (Michaelis–Menten) form:

credit = s(k) / s(n) ,   s(x) = x / (x + h) ,   default h = 1 point

Properties, by construction rather than by cases: k = 0 → credit exactly 0 (a fully missed object is penalized in full); k = 1 → credit ≈ 0.5 (the first point carries the existence information — the single most valuable point); each further point adds less; k = n → credit exactly 1. The half-saturation constant h is the only parameter (spec-versioned) and sets how strongly the first points are rewarded.

Partial-detection score = mean credit over instances, per class × range bin. Complementary to mIoU, never a replacement for it.

Implementation notes
  • Diagnostic only, by decision: it rewards partial answers, so it never enters release gates or headline suites — it exists to debug small-object recall, not to rank models.
  • Detection GT boxes group points into instances (LiDAR seg GT carries no instance IDs); target classes: pedestrian, bicycle, motorcycle, traffic cone.
  • Instances below a minimum point count are excluded and reported as a count (fail-loud, no smoothing).

Neighbourhood-tolerant error rate

AMLseg3d

Point-wise GT labels are not pixel-perfect, and for driving it does not matter if a handful of points flip class as long as the right class is present right there. This metric forgives exactly that: a misclassified point is not counted as an error if the model predicted its true class on another point within a small radius. Only misclassifications with no correct-class neighbour — a genuinely wrong region, not annotation jitter at a boundary — survive as errors.

The math

For each point p with GT class g(p) and prediction ŷ(p), define the tolerant error indicator with radius r (default 0.2 m):

err_r(p) = 1  iff  ŷ(p) ≠ g(p)  AND  ∄ q : ‖q − p‖ ≤ r ∧ ŷ(q) = g(p)
tolerant error rate = Σ err_r(p) / #(valid points)

In words: a point is an error only if the model got it wrong and did not predict the correct class anywhere within r. At r = 0 this is exactly the ordinary error rate; larger r forgives boundary jitter and annotation noise. Reported per region / range like every point metric, and it can feed the error-cluster count so a tolerated point never seeds a phantom.

Implementation notes
  • Reads the cached per-point coord + pred + target; the neighbour test is one fixed-radius cKDTree query over the misclassified points against the points predicting each target class — the same spatial machinery the error-cluster and partial-detection metrics already use.
  • r is a spec-versioned parameter; the tolerance is one-sided (it only ever removes errors), so the tolerant rate is always ≤ the strict error rate.
Region variants apply here too. Like every metric in this plan, the uncertainty metrics below are reported whole-scene and per lanelet region — road, walkway, and both — via the region filter defined in Section 5. The confident-error rate in particular reads naturally per region (confident errors on the road versus on the walkway).

Calibration error (ECE)

AMLdet3dseg3d

A model that says “90%” should be right about 90% of the time. When it is not — when it is confidently wrong — downstream logic trusts a mistake. Expected Calibration Error measures that gap between confidence and correctness, on both tasks: in seg3d the confidence is the per-point max-softmax and “right” means the point's class is correct; in det3d the confidence is the detection score and “right” means the box is a true positive (so a bin's accuracy is its precision).

The math

Bin the predictions by confidence into M bins; per bin compare mean confidence to the empirical correctness rate:

seg3d:   conf = max softmax, correctness = point-class correct
det3d:   conf = detection score, correctness = box is a true positive (⇒ acc(b) = precision(b))
ECE = Σb=1..M (n_b / N) · | acc(b) − conf(b) |

Reported overall, macro-averaged per class (so a dominant class does not hide the rest), and per range bin × region variant. DDP-clean: each bin's (confidence-sum, correct-count, count) are summable accumulators. M is a spec-versioned parameter (default 15 bins).

Implementation notes
  • seg3d reads the per-point softmax from the test point-cache; det3d reads each prediction's score + TP/FP outcome from the match state — no new accumulation.
  • Release-relevant (a gate candidate); note it is temperature-dependent, so it measures calibration as shipped, before any post-hoc recalibration.

Uncertainty usefulness (entropy AUROC)

AMLdiagnosticseg3d

Uncertainty is only worth anything if it flags the model's own mistakes — then downstream can hesitate where the model is unsure. This checks whether per-point entropy actually separates correct points from wrong ones. A model with great mIoU but random entropy is silently unsafe; this metric catches that.

The math

Per point, the normalized predictive entropy of the softmax distribution:

H = − Σc p_c · ln p_c / ln C ∈ [0, 1]

Treat H as a score for the binary task “is this point misclassified?” and report the AUROC, plus the mean entropy of correct vs misclassified points. 0.5 AUROC means the uncertainty is meaningless; higher means entropy is a usable error flag. Computed at compute() from the cached points (not summable — the point cache makes it feasible at test).

Implementation notes
  • Diagnostic, not a gate: it characterises the uncertainty signal, it does not rank model accuracy.
  • This is softmax (aleatoric-style) confidence, not Bayesian epistemic uncertainty — the latter would need MC-dropout or ensembles, a model-side change, out of scope here.

Confident-error rate

AMLdet3dseg3d

The sharpest driving-relevant one, on both tasks: of the errors the model makes, what fraction did it make at high confidence? A mistake the model is unsure about is recoverable; a confident one triggers a hard brake. It splits errors into hesitant versus confident — the confident ones are the release blockers. In seg3d an error is a point whose class is wrong and confidence is 1 − entropy (it composes with the error-cluster point extraction); in det3d an error is a false-positive box and confidence is the detection score — the confident phantom detection.

The math
seg3d:   rate = #(misclassified points with entropy H < τ) / #(misclassified points)
det3d:   rate = #(false positives with score ≥ τ_high) / #(false positives) ,   τ / τ_high spec-versioned

The area comes from the attached region / corridor filter (road / walkway / whole-scene), per range bin. det3d is false-positive only: a false negative carries no prediction and therefore no confidence, so it cannot be confident or hesitant — the missed-object (safety) axis is the critical-FN curve. On the road / corridor slice a confident error is exactly the confident phantom that triggers a hard brake.

Implementation notes
  • seg3d: shares the error-point extraction and region masks of the error-cluster metric; only adds the confidence-threshold split. Read the two together.
  • det3d: reads the score of each unmatched prediction (false positive) already produced by the matcher; no new state. Read together with the critical FP / FN curves.
  • Confident errors are the release-blocking subset of the error set on either task.

Class confusion matrix

AMLdet3dseg3d

A scalar per class hides which class the model mistakes for which — and some swaps matter for driving far more than others. The confusion matrix reads the raw true×predicted counts on both tasks: rows are the ground-truth class, columns the predicted class, so the diagonal is correct and every off-diagonal cell is a specific confusion (a truck called a bus, a barrier called a traffic cone). Read straight against the behaviour taxonomy: the same matrix is emitted per trained class and again folded to behaviour groups, where intra-group confusion collapses onto the diagonal — so the grouped matrix shows only the swaps that change the driving decision.

seg3d is point-level and needs no matching: the confusion suite already accumulates the point matrix, and this metric just emits its cells. det3d has no matrix natively, so predictions are paired to ground truth by class-agnostic greedy center-distance matching at a fixed threshold (2 m); each matched pair contributes to confusion[true, pred]. It is the label-confusion view among detections that did match — unmatched predictions (false positives) and unmatched ground truth (misses) are left to the critical FP / FN curves and are not in this matrix.

The math & slices
seg3d:   M[t, p] = #(points with true class t predicted as p)
det3d:   M[t, p] = #(matched pairs whose GT is class t and prediction is class p) ,   match: greedy center-distance ≤ 2 m, class-agnostic

Emitted as raw counts confusion_<true>__<pred> (the report row-normalizes into a heatmap, so both the count and the per-true-class rate are recoverable). Like every metric it carries the filter and range axes: the matrix is reported whole-scene, on the road slice and in the ego corridor, each split by distance band — so "what does the model confuse, and where" is one lookup.

Implementation notes
  • seg3d: a thin reader of the existing ConfusionState; the grouped suite already folds the matrix, so the grouped confusion is free.
  • det3d: reuses the criticality matcher (greedy_match) class-agnostically; the grouped suite folds labels before the state is built, so the grouped matrix needs no extra code.
  • Counts are neutral (no better/worse direction); the diagonal is the correct mass.

Section 9

Segmentation support in perception_evaluation

The runtime evaluator today covers detection, tracking, classification and point-cloud sensing checks — segmentation is absent entirely, in 2D and 3D. Segmentation feeds drivable-area and obstacle decisions on the product, so the evaluator must learn to score it. A confirmed prerequisite: the evaluator gains map-geometry access through the same cached lanelet-polygon pipeline used offline — one converter to maintain, shared by both repos. Three steps, in order:

1 · Reproduce the offline suite

Implement the autoware-ml segmentation metrics — per-class IoU / mIoU, accuracy, precision / recall / F1 — plus error clusters, the neighbourhood-tolerant error rate and the uncertainty metrics (calibration error, entropy AUROC, confident-error rate) with their region variants, all from the same versioned spec, evaluated in replay against annotated datasets.

2 · Exploit the runtime

Metrics only possible with live consecutive frames: label flicker rate — how often static-world points change class frame to frame (ego pose aligns the frames, the map says what is static) — and segmentation latency in the accuracy–latency Pareto report.

3 · Cross-task consistency

The evaluator uniquely sees detection, tracking and segmentation together: points inside a tracked object's box should carry the matching semantic class. The disagreement rate is a runtime-only health signal neither task can compute alone.

Section 10

Considered and on hold

Latency-aware AP (L-AP) — on hold, not adopted as a release metric. The paper extrapolates ground truth forward by the model's inference latency and scores predictions against that shifted world — assuming planning consumes a zero-latency snapshot of “now”.

Long term, that premise is wrong: perception outputs are timestamped, and tracking + prediction exist precisely to reason from past states into the future. Fusing latency into AP would bake a downstream defect into a perception score.

Short term, it is uncomfortably accurate: parts of today's rule-based planning behave exactly as L-AP assumes — some modules consume only the object position (not the predicted path), none consume object uncertainty, and the delay-compensation path has a known timestamp-sync gap being fixed upstream (autoware_universe PR #12979). Until that lands, an L-AP-style shifted evaluation has diagnostic value for the current stack.

Decision: planning-aware metrics are prioritized; latency-aware scoring stays on hold. Latency itself remains a first-class number, reported next to accuracy as a Pareto pair on the spec sheet (measured in perception_evaluation, where real hardware exists) — never fused. The zero-latency planning assumption is raised to the planning team as a separate issue.

Section 11

Versioning — metrics & test sets

The new metrics carry parameters — λ, horizons, radii, buffers, tier thresholds. Changing any of them silently breaks week-over-week comparability. Three rules keep the numbers trustworthy:

1 · Versioned specs

All parameters live in one versioned metric-spec (semver). Every report and spec sheet states the version it was computed with. Changing a parameter = new version + recomputed baselines, never an in-place edit.

2 · Weighted ⇒ also unweighted

Every masked or weighted number is published beside its unmasked / unweighted counterpart. Otherwise regressions in “unimportant” regions become invisible — until the weighting changes.

3 · Same spec, both repos

Both repos implement the identical, versioned spec. Parity has two levels: the shared metric core must match exactly on identical inputs; end-to-end ROS replay must stay within the spec's tolerance bands, because ROS timing is not deterministic (Section 4).

The version format

Two levels, so a report can tag every single number with the exact definition that produced it. A per-metric version travels with each value; a bundle version names the whole set the run was computed against. Metrics are keyed by their plain name everywhere (corner_error, collision_weighted_map, …) — the same name in this catalog, in a suite's output and in a report, with no short-code scheme in between to translate.

per-metric:   <metric-name>@v<MAJOR>.<MINOR>    e.g. corner_error@v1.0 · collision_weighted_map@v1.2 · error_clusters@v2.0
bundle:      metric-spec <MAJOR>.<MINOR>.<PATCH>    e.g. metric-spec 1.4.0
BumpMeansComparabilityTrigger examples
MAJOR (per-metric) The definition changed — the formula, the matching rule, or what is counted. It is a different quantity that happens to share a name. Never compare across majors. A trend line must break at the version change, not step silently. corner-distance replaces center-distance matching; error_clusters switches from “any pred≠target” to a class-set rule; the credit curve s(x) changes shape.
MINOR (per-metric) Same definition, a parameter value moved. Numbers shift but remain the same kind of measurement. Comparable only within the same id@vMAJOR.MINOR; baselines are recomputed on bump. λ 0.5→0.4; corridor horizon 4 s→3 s; ECE bins 15→20; region border-margin 0.2→0.3 m; flip threshold π/2→2π/3.
PATCH (bundle only) Nothing numeric changed — docs, performance, a refactor that leaves every value bit-identical. Fully comparable; no baseline recompute. faster boundary query; renamed an internal helper.

The bundle version is not a free-standing number: its MAJOR/MINOR is the roll-up of the metric bumps it contains (any metric MAJOR ⇒ bundle MAJOR; else any metric MINOR ⇒ bundle MINOR; else PATCH). One line at the top of a report — “computed with metric-spec 1.4.0” — plus the per-metric tag on each value is enough to reconstruct exactly how any figure was produced.

How a report carries it

The release report embeds one metric_spec block next to the results, keyed by metric name; every metric section prints its name@vX.Y, and the parameter table is the config chips already shown per metric. Trend charts key each series on (metric-name, version) so a version change is visible as a break, never a silent shift.

metric_spec: {
  bundle: "1.4.0",
  metrics: {
    "corner_error":         { version: "1.0", params: { tp_threshold_m: 2.0, assignment: "cyclic-min" } },
    "collision_weighted_map": { version: "1.2", params: { lambda: 0.5, horizon_s: 4.0, dt_s: 0.1, max_lateral_accel: 3.0 } },
    "error_clusters":      { version: "1.0", params: { cluster_radius_m: 0.5, min_cluster_points: 1 } }
    …
  }
}

The metric name is the stable key (corner_error, collision_weighted_map, … — the same names the suites already emit in their keys), so the spec scales to hundreds of metrics without a hand-maintained id scheme. Rule of thumb for the author: if you touched a number in Section 7's config chips, you bumped a MINOR; if you touched a formula or a match rule, you bumped a MAJOR.

The test set is versioned too

A number is only meaningful as a triple — (value, metric-spec version, test-set version). The metric-spec fixes how a metric is computed; the test set fixes what it was computed on. Comparing two models across a change in either is invalid, so the eval dataset carries its own version on exactly the same rules.

test-set:   <name>@v<MAJOR>.<MINOR>    e.g. det3d@v0.1 · seg3d@v0.1 · seg3d-det3d@v0.1
BumpMeansComparability
MAJOR The population changed in a way that shifts what “good” means — scenes added or removed, a re-labelling, a taxonomy or split change. Never compare a model across a test-set major; the baseline is re-run on the new set.
MINOR An additive top-up that leaves existing frames intact — extra scenes appended, a metadata fix. Comparable with care; the safe path is to re-run baselines and note the version on every number.

A test set also has a task scope — det3d, seg3d, or both — because our datasets do not all carry both annotation kinds (Section 12): a det3d-only test set simply has no segmentation numbers to report. A report therefore selects a test set first, and every section, chart and slice follows from it; a model evaluated on det3d@v0.1 is never plotted beside one on seg3d-det3d@v0.1. Changing a test set is a new versioned entry, never an in-place edit — the same discipline the metric-spec follows.

Rollout phases

Four phases. Everything we run today is Phase 1, on the one reachability model of Section 4; later phases add the temporal metrics that need a continuous stream, port the whole set to the runtime evaluator, and finally optimize throughput (faster kernels + parallel compute).

PhaseDeliverablesGated onRepo
1 All current metrics. det3d: mAP · mAPH · NDS · TP errors · corner displacement · heading flips · nearest-surface error · critical FP / FN · collision-risk-weighted mAP · calibration error · confident-error rate. seg3d: IoU · accuracy · PRF1 · error clusters · partial detection · tolerant error rate · calibration error · entropy AUROC · confident-error rate. Plus the region & corridor filters. The collision-risk metrics use the one reachability model (Section 4). Runs on the current test data. (Partial detection needs a det3d + seg3d test set; everything else is live.) AML
2 Per-instance stability & consecutive-miss streaks. A continuous stream. Following one object frame to frame needs the stable instance token surfaced from the T4 database (box3d_instance_id) into the info pkl (a regeneration) + scene-grouped per-instance state. AML
3 The whole set ported to perception_evaluation (runtime): online ego + live-tracker providers, segmentation support, latency Pareto reporting. A shared metric-spec package + lanelet & segmentation-GT loading in the evaluator; ROS timing is non-deterministic, so end-to-end parity is tolerance-banded (Section 4). APE
4 Performance & scaling. Throughput only — no metric or number changes. Faster spatial kernels (e.g. voxel-hash neighbourhoods in place of per-frame KDTree rebuilds), reuse of one spatial index per frame across the point-level metrics, and parallelizing the end-of-eval compute() across cores for the heavy point-cloud suite. A profiling pass, plus a parallel-safe and deterministic compute path (bit-identical to the serial one) so reproducibility is preserved. Purely an optimization layer over the existing metrics. AML
