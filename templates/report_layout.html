        How to add a release to this report

        1. Export the metric report — the flat key → value dict the suites produce, keyed exactly as emitted ([filter/]name_range), one bucket per suite prefix. Convert every NaN to null (JSON has no NaN; the report renders it as “–”, meaning no support there).
        2. Pick the test set the run belongs to and append a model object to its models array (name, date, commit links, artifacts, eval config, and the metric buckets). A test set's tasks controls which metric sections appear for it.
        3. Fill the test set's taxonomy (the classes and behaviour groups the release was scored on), its dataset (frames, scenes, per-class distribution) and its metric_spec. Versions travel by metric name, never a catalog id.
        4. Everything updates from that block: the test-set tabs and info, the lineage row, a bar in every chart, a column in the appendix, and the headline deltas comparing newest to previous.
        5. Keep at most 4 models per test set; fold older releases out when adding a fifth — series colors are fixed by position and more than four bars per group stops being readable.

        A test set is itself versioned (version): results are only comparable within the same test set at the same version. Changing its frames, scenes or labels bumps the version — a new test set entry, never an in-place edit — exactly as a metric change bumps the metric-spec.

        Producing the block automatically. Rather than hand-editing, keep each release as a JSON file against the versioned report-data schema (documented in the metrics proposal), then build a report by parsing one or more of them into a copy of this layout. Files are read in order, so passing several releases plots them side by side for comparison; the last is the current release and defines the test set the page describes (its vocabulary, dataset and metric spec), while older releases show “–” wherever they carry no key for a row:

        Section 3

        How to read this report

        Five things repeat on every chart, so they are explained once here: the range tabs, the taxonomy tabs, the evaluation slices (region, corridor and collision filters), the direction of better, and what a missing value means.

        Range tabs

        The sticky control bar scopes every chart, tile and delta on the page to one distance band around the ego vehicle: the full evaluated area (0–121 m) or one of three rings (0–50, 50–90, 90–121 m). A model that wins overall can still regress at far range — switch the tab to check. Chart axes keep the same scale across tabs, so bar lengths stay comparable when switching.

        Taxonomy tabs

        The same metrics are computed over two class taxonomies, and the taxonomy tab scopes the whole page to one of them:

        • Per class — every trained class scored on its own. A car predicted as a truck is a false positive for car and a false negative for truck. This is the strict view the model is trained and optimised against.
        • Behaviour groups — classes whose confusion does not change how the vehicle drives are folded into one group before scoring, so intra-group confusion becomes a hit: a bus predicted as a truck is correct for grouped_vehicle. Group names carry the grouped_ prefix; the groups of the active test set and their members are listed in Section 1. This view answers "does the model see the kind of thing that matters for the driving decision", separate from whether it names it exactly.

        Both taxonomies apply the same ground-truth filters (point count, range) to the trained classes; the fold happens afterwards, at metric time. The grouping is a reporting axis, not a training change — the model still predicts the trained classes.

        Evaluation slices

        Besides the whole scene, every metric is also reported inside lanelet-map regions, inside the straight corridor ahead of ego, and inside the collision area — the ego's reachable region clipped to the road. A slice never changes the metric — only which objects or points it counts. Scenes that ship no lanelet map are excluded from the region and collision slices (their objects and points still count whole-scene; the straight corridor needs no map and covers every scene), and each filter logs how many frames it ran on — so a slice over partial map coverage is visible, and its class mix can differ from whole-scene.

        Slices in this report whole scene — no filter road — lanelet regions [road, road_shoulder, crosswalk, drivable_area, intersection_area, crosswalk_polygon] walkway — [walkway] lanelets (sparse by design) corridor — straight strip ahead of ego (3 m wide, no map) collision area — ego reachable region ∩ road (lane speed limit, bounded steering)

        Direction, bold, and missing values

        • Direction of better — score-type metrics (AP, IoU, NDS, AUROC…) are higher-is-better ↑; error-type metrics (mATE, corner error, flip rate, ECE, error rates…) are lower-is-better ↓. Each chart states its direction; the appendix bolds the best value per row accordingly.
        • Green / red delta — the small ▲ / ▼ beside the newest release's bar is its change against the previous release, coloured by that metric's direction (green = better, red = worse). It is omitted when there is no previous release or the previous one ran on a different (incompatible) test set.
        • Missing value (–) — the metric had no support there: an empty slice (walkway in scenes without walkway lanelets), an empty range bin, or a class with no ground truth. It is absence of data, not a zero score.
        • Grayed “not measured” panels — the metric exists in the framework but was disabled for this run; the panel stays so the report layout is stable across releases.
        • Configuration chips — every metric section lists the exact evaluation settings it ran with (thresholds, margins, horizons), so numbers are only ever compared like-for-like.

        How releases are coloured

        On every chart, colour identifies the model and brightness identifies the release, so a model's history and a cross-model comparison (e.g. PTv3 vs BEVFusion) read at a glance:

        • Each distinct model gets one base hue — PTv3, BEVFusion, … each a colour of its own.
        • The newest release of a model keeps the full, vivid base hue, so it stands out as the one under review.
        • Earlier releases of the same model are the same hue muted toward the surface — present for the trend, visually stepped back so they don't compete with the new one.
        • A release evaluated on a different test-set major version (whose numbers may not be comparable) is muted much further and tagged different test set — it still appears, but the strong fade warns that comparing it may be inappropriate.

        A model's identity comes from its model field (releases sharing it share a hue); the test-set comparability from an optional per-release test_set_version checked against the active test set's version.

        Detection metrics det3d

        All detection metrics share one matching backbone: predictions are greedily matched to ground truth by BEV center distance, and every metric below reads those matches. Ground truth carries the detection classes of the database taxonomy the test set is bound to (Section 1 lists them with their behaviour groups); boxes are filtered by lidar point count and per-class range before scoring.

        Average precision — mAP and per-class AP

        det3d

        The core detection score: for each class, predictions are ranked by confidence and matched to ground truth; the area under the resulting precision–recall curve is the AP. It rewards finding every object (recall) without inventing ones that are not there (precision). mAP averages over the four match thresholds and then over classes — the single number, with the per-class bars showing who pays for it.

        Heading-aware quality — mAPH and NDS

        det3d

        mAPH is AP where every true positive is discounted by its heading error — a detection pointing the wrong way earns less credit, because downstream tracking and prediction consume the heading. NDS blends mAP with the true-positive errors (translation, scale, orientation, velocity) into one composite release number.

        True-positive errors — mATE, mASE, mAOE, mAVE

        det3d

        For the objects the model did find, how good are the boxes? Four independent error axes: center position (ATE, meters), size (ASE, 1−IoU after alignment), orientation (AOE, radians) and velocity (AVE, m/s). Finding everything with sloppy boxes and finding less with tight boxes are different failure modes — these separate them.

        Corner displacement error

        det3d

        Position, size and yaw errors interact — a box can have a perfect center and still put its corners in the wrong lane. Corner displacement folds all three into one number in meters, measured where planning collides with things: the box outline. A 3° yaw error on a 20 m truck shifts a corner ~0.5 m, and that shows up here directly.

        Config TPs matched at 2 m center distance cyclic corner assignment (min over 4 rotations) lower is better ↓

        Corner error m, lower ↓

        Heading-flip rate

        det3d

        A 180° heading flip leaves the box outline almost unchanged, so corner error forgives it — but it inverts the object's perceived direction of travel and is a prime cause of tracking failures. Any true positive whose heading error passes a quarter turn counts as one flip — a uniform +1 however far past 90°, because wrong-way is wrong-way regardless of degree.

        Config TPs matched at 2 m flip when |Δψ| > π/2 lower is better ↓

        Heading-flip rate fraction of TPs, lower ↓

        Signed nearest-surface error

        det3d

        Stopping distance is computed against the nearest face of an object, not its center. The same 1 m center error is harmless if the box is too long at the back, and dangerous if the near face is placed 1 m too far away — ego brakes late. The sign of this error is the safety signal. The measure is radial — the distance from the ego origin to the nearest point of the box footprint — so it applies to objects in any direction (beside and behind, not only ahead); the figure shows an object in front for clarity.

        Critical FP / FN — errors in ego's path

        det3d

        Two numbers we never average: false positives in ego's path cause phantom braking (usability); false negatives in ego's path mean driving toward something we can't see (safety). "In path" is the one reachability model: every agent and ego propagated at the lane speed limit under bounded steering, and an object is critical when its reachable set can meet ego's within the horizon — a finite time-to-collision. Both are counted per frame over frames whose scene has a lanelet map.

        Collision-risk-weighted mAP

        det3d

        mAP where every object's contribution is weighted by how soon it could collide with ego — an object 1 s away weighs e−0.5 ≈ 0.61, one 3 s away ≈ 0.22, and anything unreachable within the 4 s horizon weighs 0 — so a model can no longer buy score with easy, irrelevant objects (a same-speed lead can never be caught: TTC = ∞). Always read next to the unweighted mAP above.

        Occlusion-aware recall split

        det3d

        A miss on an object that returned no lidar point is a physics problem; a miss on a visible object is a model problem. The same detection suite runs twice with different ground-truth point-count floors: the visible split keeps boxes with at least one lidar point, the overall split keeps every box including fully occluded ones. The gap between the two APs is the occlusion effect on recall; the release number stays the main suite with its floor of two points.

        Config visible: GT min lidar points ≥ 1 overall: GT min lidar points ≥ 0 per trained class only, no behaviour-group twin higher is better ↑

        Per-class AP — visible vs overall AP, 0–1, higher ↑

        Calibration error (ECE)

        det3d

        A 0.9-score box should be a true positive about 90% of the time. When it is not, downstream logic trusts a score it should not. ECE measures that gap between the detection score and the empirical precision — the detection twin of the segmentation calibration metric.

        Two averagings are reported. ECE pools every detection into the score bins, so the classes that dominate the data — cars here — dominate the number. Macro ECE computes the same binned gap per class and averages the classes with equal weight, so a rare class that is badly calibrated cannot be hidden behind a common one that is well calibrated. The two are equal only when calibration quality is uniform across classes; read the gap between them as how uneven it is.

        Config 15 score bins correctness = box is a true positive (bin accuracy = precision) ECE: detection-weighted · macro ECE: per class, equally weighted lower is better ↓

        Detection calibration error lower ↓

        Confident-error rate

        det3d

        Of the boxes the model got wrong, what fraction was it sure about? A false positive the model is unsure of is recoverable; a high-score false positive is the confident phantom that triggers a hard brake. This is the detection twin of the segmentation confident-error rate — an error here is a false-positive box, and confidence is the detection score.

        Config confident = score ≥ 0.5 error = false positive (no matching GT) lower is better ↓

        Confident false-positive rate fraction of FPs, lower ↓

        Class confusion matrix

        det3d

        Among detections that match a ground-truth box (class-agnostic, within 2 m), which class does the model assign? Rows are the true class, columns the prediction — the diagonal is correct and each off-diagonal cell is a specific swap. Cells are row-normalized (of all matched true-class objects, the fraction called each class); hover for the raw count. Follows the range and taxonomy tabs, so the grouped taxonomy collapses intra-group swaps onto the diagonal. Misses and false positives are not here — they are the critical-FP/FN metric. With more than one release on the test set, Δ vs previous swaps the cell values for the change since the previous release, coloured green where the model improved and red where it regressed.

        IoU, accuracy and the per-class view

        seg3d

        IoU per class is the overlap between all points predicted as a class and all points that truly are that class — it punishes both painting too much and missing points. mIoU averages the classes with support. Overall accuracy (aAcc) is the plain fraction of correctly labeled points, dominated by the big surfaces; mean accuracy (mAcc) averages each class's own accuracy equally, so a rare class counts as much as the road. fwIoU weights classes by how many points they own, so it tracks the big surfaces.

        Error clusters — phantom obstacles

        seg3d

        An error is simply a point whose prediction disagrees with the ground truth; what makes it dangerous is where it happens, and that comes from the slice, never from class sets. On the road slice these are the phantoms that brake the car and the mislabeled obstacles that hide one. Nearby error points merge into one cluster, and each cluster counts once regardless of size — a lone stray point and a ten-point blob both cause a single emergency stop.

        Point error rate fraction, lower ↓

        Small-object partial-detection score

        seg3ddiagnostic

        For a pedestrian or a traffic cone, classifying even a handful of points correctly is far better than classifying none: downstream logic can still react. Point-averaged mIoU cannot see this. Per small-object ground-truth box, the first correctly classified point earns about half the credit (existence) and further points saturate toward one; a box with no correct point scores exactly zero. It needs detection boxes and point labels on the same frame, so it exists only on a joint test set. Diagnostic only, never a release gate.

        Config credit = s(k) / s(n), s(x) = x / (x + 1) boxes with no interior point are skipped and counted per trained class only, never grouped higher is better ↑

        Partial-detection score mean credit per box, 0–1, higher ↑

        Neighbourhood-tolerant error rate

        seg3d

        Point labels are not pixel-perfect, and a few flipped points do not matter for driving as long as the right class is present right there. A misclassified point counts as an error only if the model predicted its true class on no point within a small radius — a genuinely wrong region, not annotation jitter at a boundary. Always ≤ the strict error rate; it equals it at radius 0.

        Calibration error (ECE)

        seg3d

        A model that says “90% road” should be right about 90% of the time. When it is not — when it is confidently wrong — downstream logic trusts a mistake. Expected Calibration Error measures the gap between confidence and correctness.

        Two averagings are reported. ECE pools every point into the confidence bins, so the classes that carry the most points — road and ground — dominate the number. Macro ECE computes the same binned gap per class and averages the classes with equal weight, so a rare class that is badly calibrated cannot be hidden behind a common one that is well calibrated. That is why the macro value is the larger one here: pooled calibration looks excellent because most points belong to a handful of easy, well-calibrated classes.

        Config 15 confidence bins measured as shipped — before any recalibration ECE: point-weighted · macro ECE: per class, equally weighted lower is better ↓

        Calibration error lower ↓

        Uncertainty usefulness (entropy AUROC)

        seg3d

        Uncertainty is only worth anything if it flags the model's own mistakes — then downstream can hesitate where the model is unsure. This checks whether per-point entropy actually separates correct points from wrong ones: 0.5 means the uncertainty is meaningless noise, 1.0 means it is a perfect error flag. Diagnostic — it characterizes the confidence signal, it does not rank accuracy.
